Siglum

Code walkthrough.

This deck traces the path a change takes through Siglum, file by file. Each box in the diagrams names the module that does the work.

END TO END

The full path, from a pull request to a signed verdict.

Each stage is detailed in the slides that follow. The trusted stage never runs the pull request's code. The seal stage is wired into the gate: on a success it signs and self-verifies before a green check, against staging Sigstore.

1 · GATHER

The gather job collects evidence in the pull request, with no access to secrets.

# validators/run.py · runs over head, contents:read only, no secrets
change = Change(repo=$GITHUB_REPOSITORY, base_sha=$GITHUB_BASE_SHA, head_sha=$GITHUB_SHA)
ctx = ValidationContext(change, workspace, changed_files)
results = (SecretScanValidator().run(ctx),)
payload = {"validators": [...]}  # observations only
return 0 if all PASSED else 1

It emits results.json with the validator observations only. It can fail the build, but it does not produce the verdict, and it reports no security-relevant fields: the trusted stage reads the head version of every anchored path itself, so a gather that lies cannot weaken the gate.

DATA MODEL

The core data types are immutable dataclasses with no behavior and no I/O.

models.py imports only the enum definitions. Everything from outside the core arrives as evidence and leaves as signed output.

2 · ASSESS

A single pure function, assess(), turns an evidence bundle into a verdict.

# derive.py · assess(bundle) -> Assessment
verdict:     required ERRORED → ERROR · required FAILED → FAIL · else PASS
coverage:    required not in {PASSED, FAILED} → gap → INCOMPLETE
independence: validator_authority matches the org-pinned gate_identity → SATISFIED, else UNMET

merge_eligible = verdict==PASS and coverage==FULL and independence != UNMET

Given the same evidence, assess() returns the same result every time. It does not read the clock, the network, or the filesystem.

DECISION HASH

The decision hash covers only the fields that determine the verdict.

It deliberately excludes timestamps and run identifiers, which is what lets someone holding only the attestation recompute it.

3 · THE GATE

The trusted gate runs a sequence of fail-closed checks.

Any failed check blocks the merge with a readable reason. The gate never checks out the head commit.

ANCHORING

Every policy input is read from the protected base commit.

In gate/anchor.py, the head version of each path is read from the trusted forge at the head sha, not taken from the gather. A head commit that edits an anchored path is recorded as an override attempt and is otherwise ignored.

MISSING VALIDATORS

A required validator that is missing from the evidence is recorded as UNKNOWN.

# gate/orchestrate.py · _fill_missing_required
for vid in base_required_ids:
    if vid not in present:
        add ValidatorResult(vid, status=UNKNOWN, required=True)

# UNKNOWN is not DEFINITE → coverage gap → INCOMPLETE → blocks

Because the base policy lists the validator as required, a head commit cannot remove it by simply not running it.

RECOMPUTE BEFORE SIGN

The verdict is recomputed from the evidence before it is trusted.

This lives in verify.py, and seal() calls it first, so a forged verdict raises an error before any signing happens.

4 · PREDICATE + SIGN

The predicate is built from the assessment and then keyless-signed through Sigstore.

This is predicate.py and sealing/seal.py. The subject digest is the decision_hash because Sigstore accepts only SHA-2 digests. Signing is pinned to Sigstore staging until a reviewed change wires production.

5 · VERIFY OFFLINE

Offline verification checks the identity policy and the verdict, not only the signature.

In sealing/verify_signed.py the decision_hash is recomputed from the predicate body, so a verifier holding only the file can detect an attestation whose recorded verdict does not match its evidence.

PACKAGE MAP

The package is organized so that dependencies point inward, toward a pure core.

The core imports only the enum definitions. The outer rings depend on the core, and the core does not depend on them.

PURE CORE

The pure core does not read the clock, the network, or any signer.

EvidenceBundle ──▶ assess ──▶ Assessment ──▶ verify (recompute)

models · verdict · derive · canonical · verify · predicate

Because the core is pure, it is replayable. Re-running any decision offline produces the identical decision_hash, which is what lets someone else check the proof.

SEAMS

The core reaches the outside world through three seams.

The security logic is unit-tested. The four external bindings are integration-gated and are not stubbed into passing unit tests.

DECISION-HASH INVARIANT

The same decision payload is recomputed independently in three places.

verify_signed mirrors derive byte for byte (validators sorted by id, then version). Any drift between them is the one thing that would matter, so it is pinned by tests.

TRUST BOUNDARY

The trust boundary is enforced as a boundary between two CI jobs.

The author's code runs only in the gather job. The job that decides and signs does not run the author's code and holds nothing the author's code can reach.

WIRED VS GATED

What is covered by unit tests, and what is integration-gated.

Pure and unit-tested

derive, verify, anchor, mergeable_subject, enforce, the decision-hash recompute, and the empty-identity-policy rejection. The security logic runs in CI.

Build-time seams, integration-gated

GitHub REST fetch, Fulcio and Rekor signing, Sigstore verify_dsse, and the GitHub App. Signing is pinned to Sigstore staging.

No external dependency is stubbed into a passing unit test, so the results reflect what actually runs. When the policy requires approval, the gate reads the PR reviews with its own token and enforces the force-push (TOCTOU) defense in real runs; the remaining caveat is that signing runs against Sigstore staging, only in a live CI run.
