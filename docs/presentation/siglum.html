Siglum

Siglum makes a pull-request gate explain and prove its decision.

When GitHub says a check passed, you know a status was reported. Siglum records what was checked, which policy was used, which commit was evaluated, and why the final merge decision can be verified later.

Siglum is Apache-2.0, builds on Sigstore and in-toto/SLSA, and runs in your organization's CI rather than through a Siglum-hosted service.

Problem

A green check tells GitHub that a named check finished successfully, but it does not explain whether the important validation actually happened.

Why this happens

This gap usually comes from normal CI behavior, not from anyone forging GitHub or breaking cryptography.

1 · It only sees the name

The gate trusts that a status called ci finished. It never checks what actually ran behind it.

2 · The PR edits its own gate

If the workflow, test command, scanner config, or a suppression lives in the PR, the author can weaken it.

3 · Silence looks like success

Skips, path filters, continue-on-error, and empty artifacts can all leave a green-looking box.

Concrete example

The risky case is a pull request that changes both the code and the workflow that is supposed to judge that code.

One PR, two changes

The same branch asks to merge code and edits the workflow that says whether that code is safe to merge.

The enforcement rule is inside the same change it is trying to enforce, so the author can weaken the test before the gate reads the result.
.github/workflows/ci.yml
- run: npm test && semgrep scan
+ run: echo "tests passed"
+ continue-on-error: true

What Siglum checks

Siglum tries to make the final decision recomputable, fail-closed, tied to one commit, and independent of the PR author.

Recomputed from evidenceSiglum recomputes the verdict itself. A result that's just handed to it gets rejected.
rejects: a handed-over green status.
Fail-closedSkipped, errored, or absent evidence is never a pass.
blocks: silently dropping the scanner.
Change-boundTied to the exact commit being merged, including the merge-queue candidate.
prevents: approving one commit and merging another.
IndependentGate-critical checks run where the PR can't edit them.
blocks: editing the gate in your own PR.

Trust boundary

The pull request is allowed to produce evidence, but a separate trusted job decides what that evidence means.

The untrusted job can hand over observations. The trusted job recomputes the decision from those observations and the base policy.

Sigstore context

Siglum uses Sigstore for signing and adds a validation attestation that says what was checked.

In this diagram, the validation attestation is the part Siglum adds. Fulcio, Rekor, and Cosign are existing Sigstore pieces that Siglum relies on.

Problem

Sigstore can prove which workflow signed a statement; Siglum makes sure the statement is a real validation decision before it is signed.

Sigstore and SLSA already give you

A keyless signer identity (Fulcio), a public transparency log (Rekor), a signature over whatever bytes you hand it (Cosign), and a record of how an artifact was built (SLSA).

What's still missing

A trustworthy verdict that the change was actually validated: computed from evidence, fail-closed, and tied to the exact commit. Plus a gate that blocks the merge when that verdict isn't there.

Sigstore signs bytes you hand it. Siglum first recomputes the gate result from evidence, so the signed payload is a validation decision instead of an unchecked claim.

After the run

After CI finishes, the signed attestation can still be checked by someone who was not present for the run.

$ cosign verify-attestation --type https://siglum.dev/ValidationAttestation/v0.3 \
    --certificate-identity-regexp '^https://github.com/your-org/' artifact
Verification succeeded.

Scope

Siglum proves that a specific validation process ran; it does not prove the code is safe or that the tests are good.

It proves

The declared validators ran to completion over a specific change, under a policy anchored to the base and independent of the author, and the verdict recomputes from the pinned evidence.

It does not claim

That your tests are meaningful, your code is safe, or your dependencies are sound. It also can't stop a compromised org admin from redefining trust.

That boundary matters: the proof says the declared checks ran under the declared policy, not that the checks were sufficient for every risk.

End state

The goal is that when a change says it was validated, someone else can check that claim.

Start by auditing an existing repository. Move from preview mode to Sealed mode only when the organization is ready to make the proof enforceable.

Siglum

How the implementation turns pull-request evidence into a signed gate decision.

This track follows one change through the implementation. Each slide names the module that performs the step, so the walkthrough stays tied to the code.

End-to-end path

A pull request first produces observations; then the trusted gate recomputes, signs, and publishes the decision.

The important boundary is between observation and decision. The gather stage can run on the PR; the trusted stage never checks out PR code, and it signs only after it has recomputed the decision itself.

Core data

The core passes plain immutable data around, which makes the decision logic easy to replay and test.

The model layer does not fetch from GitHub or talk to Sigstore. Outside systems are converted into evidence before the core sees them.

1 · Gather

The gather job runs in the pull request and collects observations, but it has no secrets and does not decide whether the PR can merge.

# validators/run.py · runs over head, contents:read only, no secrets
change = Change(repo=$GITHUB_REPOSITORY, base_sha=$GITHUB_BASE_SHA, head_sha=$GITHUB_SHA)
ctx = ValidationContext(change, workspace, changed_files)
results = (SecretScanValidator().run(ctx),)
payload = {"validators": [...]}  # observations only
return 0 if all PASSED else 1

It emits results.json with validator observations. It can fail the build, but it does not produce the verdict: the trusted stage pins required and version from the base policy and reads the head version of every anchored path itself, so a gather that lies cannot weaken the gate.

2 · Assess

assess() is the pure function that converts an evidence bundle into the gate verdict.

# derive.py · assess(bundle) -> Assessment
verdict:     required ERRORED → ERROR · required FAILED → FAIL · else PASS
coverage:    required not in {PASSED, FAILED} → gap → INCOMPLETE
independence: if required, validator_authority must match gate_identity; otherwise NOT_REQUIRED

merge_eligible = verdict==PASS and coverage==FULL and independence != UNMET

Given the same evidence, assess() returns the same result every time. It does not read the clock, the network, or the filesystem.

Decision hash

The decision hash includes the fields that determine the verdict and leaves out run-specific noise.

Because timestamps and run identifiers are excluded, a verifier can recompute the same hash later from the attestation contents.

3 · Gate

The trusted gate checks the environment and anchored inputs before it accepts any evidence.

A failure at any step produces a blocking result with a reason. The trusted job reads PR metadata and anchored files through the forge provider; it does not execute the PR checkout.

Anchored inputs

Rules that affect the verdict come from the protected base commit, not from the pull request.

In gate/anchor.py, the head version of each path is read from the trusted forge at the head sha, not taken from the gather. A head commit that edits an anchored path is recorded as an override attempt and refused before verdict derivation.

Missing evidence

If required evidence is missing, Siglum records that as UNKNOWN and treats coverage as incomplete.

# gate/evidence.py · normalize_evidence
for spec in base_validators:
    obs = observed_by_id.get(spec.id)
    add ValidatorResult(spec.id, version=spec.version, required=spec.required,
        status=obs.status if obs else UNKNOWN, artifact_digest=obs.artifact_digest if obs else "")

# undeclared validators are ignored; duplicate ids are rejected

The required validator list comes from the base policy, so the PR cannot make a validator disappear by omitting it from results.json.

Before signing

Before signing, Siglum recomputes the verdict from the evidence and refuses mismatches.

seal() calls verify.py before signing. If the recorded assessment does not match the evidence bundle, signing never starts.

4 · Attestation and signing

The attestation is built from the assessment and then signed with Sigstore keyless signing.

predicate.py records the commit as the in-toto subject. sealing/seal.py signs a statement whose subject digest is sha256(decision_hash), with the commit kept in the subject name and predicate body. Signing is pinned to Sigstore staging until a reviewed change wires production.

5 · Offline verification

Offline verification checks both the Sigstore identity and whether the recorded verdict still recomputes.

In sealing/verify_signed.py the decision_hash is recomputed from the predicate body, so a verifier holding only the file can detect an attestation whose recorded verdict does not match its evidence.

Package layout

The package is arranged so the security-critical core does not depend on GitHub or Sigstore clients.

The pure core has no I/O: models carry data, authority is pure matching, and derive, verify, and predicate operate on those values. The outer rings depend on the core, and the core does not depend on them.

Pure core

The pure core avoids clocks, networks, and signers so the same evidence always gives the same result.

EvidenceBundle ──▶ assess ──▶ Assessment ──▶ verify (recompute)

models · verdict · authority · derive · canonical · verify · predicate

That purity is what makes replay possible: the same inputs produce the same decision hash during CI and during offline verification.

Integration seams

GitHub, validators, and Sigstore enter through narrow seams around the pure core.

The security logic is unit-tested. The GitHub REST/App and Sigstore signing/verification bindings are integration-gated and are not stubbed into passing unit tests.

Recompute invariant

The same canonical decision payload is recomputed before publishing and again during offline verification.

verify_signed reconstructs the bundle from the predicate and calls the same assess path, including validator sorting by id and version. Any schema drift is pinned by tests.

CI trust boundary

The two CI jobs are separated so PR-authored code cannot reach the job that signs and posts the required check.

PR-authored code runs only in gather. The job that decides and signs has the App credentials and OIDC identity, but it never runs the PR checkout.

Test boundaries

The unit tests cover the pure decision logic; live services stay behind integration boundaries.

Pure and unit-tested

derive, verify, anchor, mergeable_subject, enforce, the decision-hash recompute, and the empty-identity-policy rejection. The security logic runs in CI.

Build-time seams, integration-gated

GitHub REST fetch, Fulcio and Rekor signing, Sigstore verify_dsse, and the GitHub App. Signing is pinned to Sigstore staging.

No external dependency is stubbed into a passing unit test, so the results reflect what actually runs. When the policy requires approval, the gate reads the PR reviews with its own token and enforces the force-push (TOCTOU) defense in real runs; the remaining caveat is that signing runs against Sigstore staging, only in a live CI run.

Test strategy

The tests are written around the attacker moves the gate is supposed to stop.

✓354 collected tests mirror the threat model; ruff and mypy are part of the local quality gate. Network paths are integration-gated, not faked into unit tests.
✓Each attacker move is one test driven end-to-end through the real gate over an in-memory forge: laundering, validator deletion, force-push after approve, token replay, self-hosted runners, duplicate evidence.
✓Adversarial suites for the JWT verifier and the sealing path; malformed inputs fail closed with a posted, legible failing check.
✓Whatever only runs live (signing, token minting, the REST calls) is labeled as such in the docs instead of being faked into a passing unit test.

Start with audit

You can start by running Siglum against an existing repository before installing anything there.

$ export GITHUB_TOKEN=... # read-only access is enough for most repos $ siglum audit --repo your-org/your-repo $ siglum audit --repo your-org/your-repo --json

No target-repo install

Audit reads GitHub configuration and workflow files. It does not add workflows, checks, apps, or secrets.

Works on real repos

Use it on an existing public or private repository to see where branch protection trusts checks the PR can influence.

Automation-friendly

The report has stable finding codes, JSON output, and a nonzero exit code when gaps exist.

Classic branch-protection reads may require broader GitHub read permissions, depending on the org. The target repo stays unchanged.

Audit findings

The audit report explains which required checks can be spoofed, skipped, or rewritten by a pull request.

SPOOFABLE_CHECK · a required check any token with status:write can satisfyHIGH
PR_EDITABLE_WORKFLOW · a required check produced by a workflow the PR can rewriteHIGH
UNPROTECTED_DEFAULT_BRANCH · no branch protection or ruleset at allHIGH
SILENT_SKIP · continue-on-error or path filters can green the check without running itMEDIUM
ADMIN_BYPASS · admins can bypass the required checks (noted, not defended)LOW
This first step does not install an App, add a policy file, or mutate the repository. It simply asks what the current gate actually proves.

Commands

Start with a read-only audit against a real repository. The local fixture commands work after scaffold; the CI and release commands need the artifacts produced by the Sealed workflow.

# Inspect an existing GitHub repo; use a token for private repos or full protection details.
$ siglum audit --repo org/repo

# Local fixture.
$ siglum demo scaffold --out ./demo --repo org/gate-proof-demo
$ cd ./demo
$ siglum policy lint .siglum/policy.toml
$ siglum setup check --local .

# Live install, Sealed CI, and release verification.
$ siglum setup check --repo org/repo
$ siglum gate run --results results.json
$ siglum release-check --commit "$GITHUB_SHA" --bundle siglum-attestation.bundle.json --identity-policy identity-policy.toml

audit --repo does not install anything or change the target repository. gate run belongs in the trusted CI job, and release-check --bundle expects the signed Sigstore bundle from that job.

Two modes

Dry-run is for learning what would happen; Sealed is the mode that actually protects the required check.

Dry-run

Runs in your normal CI. Shows the verdict, silent skips, and policy gaps before you wire the protected gate.

authoring · adoption · fast feedback

Sealed

Org-controlled job outside the PR's reach. Verified OIDC identity, signed attestation, base-anchored policy.

the Sealed defense

Dry-run is useful for feedback during adoption. Sealed changes who can produce the required check, which is why it is the protective mode.

Policy

The policy file states which validators matter and which files must come from the protected base.

policy_id = "default"
independence_required = true
anchor_paths = [".siglum/policy.toml", ".github/CODEOWNERS", "Makefile"]

[[validators]]
id = "secret-scan"
required = true

[gate_identity]
repository = "your-org/your-repo"
workflow_path = ".github/workflows/siglum-seal-enforce.yml"
protected_refs = ["refs/heads/main"]

A PR can propose a policy change for future merges, but the current verdict still uses the policy from the protected base.

Validators

Validators collect facts about the change; the gate decides how those facts affect merge eligibility.

Shipped

secret-scan runs in the gather job today. The command validator is built and unit-tested but not yet wired in.

Custom contract

Any tool that emits the stable validator-result JSON + artifact manifest plugs in.

Planned

SARIF ingestion, Semgrep-style static evidence, and dependency or license checks. They fit the contract but aren't built yet.

Gate-critical validators are concrete, pinned, and base-anchored in Sealed mode.

Local fixture

The local fixture lets you see the problem and the Siglum setup without touching GitHub.

$ git clone https://github.com/siglum-dev/siglum && cd siglum $ python -m pip install -e ".[dev]" # generate a fixture repo with a required check the PR can rewrite $ siglum demo scaffold --out /tmp/gate-proof-demo --repo your-org/gate-proof-demo --force $ cd /tmp/gate-proof-demo # this fixture should find one gap; audit exits 1 when it finds findings $ siglum audit --config siglum-audit-config.json || true $ siglum setup check --local .

The fixture creates a toy app, a required check produced by PR-editable CI, the Siglum policy and workflows, and a controlled bad PR patch you can inspect. The audit returning nonzero is the expected signal that the gap was found.

What the demo creates

The scaffold creates a disposable repository that contains both the vulnerable gate and the Siglum files that would close it.

1 · App codewrites service/auth.py plus a passing pytest test
2 · Hollow gateadds a required tests check produced by PR-editable ci.yml
3 · Siglum installadds policy, gather, seal-enforce, identity, audit, and setup files
4 · Bad PR patchships demo/prevention.patch: fake AWS-looking key plus echo success CI
5 · Expected resultlocal audit finds PR_EDITABLE_WORKFLOW; setup check says ready
Local mode never contacts GitHub and does not install anything outside the fixture directory. In a live Sealed install, applying the demo patch is blocked because secret-scan fails on the planted fake key, or earlier if the PR edits Siglum policy or gate workflows.

Why the fixture is vulnerable

The fixture repo intentionally uses a required test check that the PR is allowed to rewrite.

The fixture reproduces the common misconfiguration: branch protection requires a check, but that check is produced by a workflow the contributor can edit in the same PR.

The demo PR

The demo PR changes the CI command to echo success and also adds a fake secret to the app code.

.github/workflows/ci.yml
- run: python -m pytest
+ run: echo "All tests passed"
service/auth.py
+ AWS_ACCESS_KEY_ID = "AKIA…EXAMPLE"
  def issue_session_token(user_id):
      ...

That is the pattern Siglum is meant to catch: a code change and a weakened validation path arriving together in one PR.

Without Siglum

Without Siglum, GitHub can see the green tests check but not that the workflow stopped running tests.

With Sealed

With Sealed installed, the legacy tests check can be green, but the required Siglum check still blocks the merge.

If the PR also edits Siglum policy or gate workflows, Sealed rejects the PR before verdict derivation because base-anchored inputs changed.

PR feedback

The PR check should tell a developer which evidence failed or went missing, not just say no.

No one needs to understand in-toto. The check says what failed, what's missing, and what to fix.

Overrides

If someone deliberately overrides a failed gate, the override is recorded instead of erasing the failure.

Override

Requires actor and reason. Recorded inside the attestation without rewriting the original FAIL. Dispositions need expiry, actor, reason, and stay visible to auditors.

Cannot override

Signing-identity failures and independence gaps are structural. No author-waivable proof.
