Siglum

A merge gate you can prove.

Siglum turns "CI passed" from a claim into evidence anyone can verify: a derived, fail-closed, change-bound verdict, sealed into a signed attestation you can check offline with standard tools.

Open source · Apache-2.0 · built on Sigstore and in-toto/SLSA · runs in your org, no data leaves it

THE GAP

A green check tells you a check concluded. Here is what it leaves open.

Did the tests actually run?

The gate only sees that a status with the expected name showed up on the commit. What ran behind it is invisible.

Did they run on this version?

An approval or a check from an earlier commit can decorate a newer, different one. Force-push makes this cheap.

Was the scanner silently skipped?

Path filters, continue-on-error, and empty artifacts all leave a green-looking box with no validation behind it.

Who controlled the rules?

If the workflow, policy, or scanner config lives in the pull request, the author being gated also controls the gate.

THE ATTACK

Nothing is forged. The evidence is poisoned, and the check passes for real.

From a real repository audit: the required checks looked locked down, but the workflow that produces them runs on the pull request. The lock is on the inside of the door.

With AI agents authoring a growing share of pull requests, this trust is extended at machine scale.

HOW IT WORKS

The author can't grade their own exam.

THE PROOF

A signed proof that travels with the change and outlives the CI run.

Keyless, via Sigstore

Signed with the workflow's own OIDC identity through Fulcio. There are no signing keys for you to generate, rotate, or leak.

An open in-toto predicate

The validation sibling of SLSA build provenance: SLSA attests how an artifact was built, Siglum attests that the change was independently validated.

Verifiable offline

Anyone with the bundle checks it with cosign and a strict identity policy. No Siglum service in the loop. Your auditor does the verifying.

$ cosign verify-attestation \ --type https://siglum.dev/ValidationAttestation/v0.3 \ --certificate-identity-regexp '^https://github.com/your-org/' \ --certificate-oidc-issuer https://token.actions.githubusercontent.com \ your-artifact Verification succeeded.

Signing runs against Sigstore staging today. Production signing is deliberately gated behind explicit review, because it publishes to a permanent public log.

HONEST SCOPE

What it proves, and what it deliberately does not claim.

It proves

That a defined set of validators ran to completion over a specific change, under a policy that was fixed and independent of the author for the duration of the assessment, and that the recorded verdict is a pure function of that pinned evidence.

It does not claim

That your code is safe, your tests are meaningful, or your dependencies are sound. It never judges whether the validation was adequate. And it does not defend against a compromised org administrator, who can turn enforcement off.

The boundary is stated on purpose. A gate that overclaims is just another green badge.

THE CORE IDEA

The verdict is a pure function of the evidence.

# the one derivation, used by the gate, the offline verifier, and the release check assess(bundle) → verdict PASS | FAIL | ERROR coverage FULL | INCOMPLETE # any required validator without a definite status → gap independence SATISFIED | UNMET | NOT_REQUIRED merge_eligible = PASS and FULL and independence != UNMET decision_hash = sha256(canonical_json(decision_fields)) # no timestamps, no run ids
01Every consumer that touches a stored decision recomputes it first: deserialization, signing, offline verification, and the release check all rerun assess() and reject any field that does not recompute.
02The attestation carries the inputs, so it is structurally unable to disagree with its own verdict.

TRUST BOUNDARY, IN DATA

The gather artifact supplies observations. The base policy decides everything else.

head-controlled results.json says required=falsea failing validator laundered as optional
BLOCKED BY
required comes from the base policythe artifact's flag is ignored; the failure counts
head deletes a gate-critical validatorthe evidence for it simply never arrives
BLOCKED BY
absent evidence is filled UNKNOWNcoverage goes INCOMPLETE and the merge blocks
head edits the policy, config, or workflowthe validation would run under the head's rules
BLOCKED BY
base anchoring, read by the trusted jobhead digests are derived at the head SHA, never taken from the artifact; any override refuses

Duplicate validator ids reject; ids the base policy never declared are ignored. Only base-declared validators can contribute to the verdict.

THE STOP SEQUENCE

Ordered, fail-closed, and each failure posts its reason.

01Head still current: the PR is re-fetched with the gate's own token; a head that moved since the event fails closed.
02Hosted runner + approved SHA: a self-hosted runner refuses, and the approved SHA must equal the mergeable subject (the approve-A-then-force-push-B defense).
03Approval proof: a PR needs a current approval bound to its head; a merge queue proves the target branch requires review, else fails closed.
04Base anchoring: every gate-critical input is read at the protected base; a head edit to any of them refuses.
05Verified identity: the gate mints and cryptographically verifies its own OIDC token, then matches the org-pinned gate identity.
06Enforcement self-audit: the run fails unless the siglum check is actually required and source-restricted to the Siglum App.
07Evidence → verdict → seal: normalize, assess, recompute-verify, then sign and self-verify before any green check is posted.

VERIFIED IDENTITY

One predicate decides independence, everywhere.

The token is verified, never trusted

The gate mints its own Actions OIDC token and verifies it in core code: algorithm pinned to RS256 in code (no alg:none, no key-type confusion), exact issuer and audience, JWKS host pinned to the issuer, bounded clock skew.

Then the claims must match the pin

Repository, immutable repository id, exact workflow path, a protected branch or tag ref, and a hosted runner. The ref is derived from job_workflow_ref, so a stated ref is never believed on its own.

The same gate_identity_mismatch predicate powers the runtime refusal and the recorded independence verdict, so the rule that was enforced and the rule that was recorded can never drift apart.

The adversarial conformance suite rejects alg:none, key confusion, wrong issuer or audience, expiry, bad signatures, and self-hosted runners.

SIGN BEFORE GREEN

There is never a green check without a verified attestation behind it.

on any failurefail closed: a failing check, never a silent pass

Enforcement is self-audited too: a policy that requires independence with missing App credentials fails closed instead of degrading to an unrestricted token. An installed-but-unenforced gate refuses to pretend.

THE ATTESTATION

The attestation cannot lie about its own verdict.

01The predicate records the evidence: change SHAs, policy id and hash, every validator's status and artifact digest, the verified run authority, and the expected gate identity.
02A verifier reconstructs the evidence bundle from the predicate and rederives every decision field, including the hash. A stated verdict that does not follow from the recorded evidence rejects.
03Offline verification replays the gate's own authority floor, so an attestation from a self-hosted runner or the wrong repository rejects even with a valid signature.
04A missing or empty identity policy rejects. A valid Sigstore signature by itself is never sufficient.

BOUNDARY + STATUS DISCIPLINE

Defended, not defended, and how each claim is labeled.

Defended

A contributor with push access who can edit CI in their own pull request, without admin or bypass rights. That includes an AI agent operating with those permissions.

Out of scope, stated

A compromised org administrator. Validators that execute head-authored code (which is why the default gate-critical validator is the read-only secret scan). Whether your validation was adequate.

TEST CULTURE

The tests mirror the threat model.

✓299 tests, strict mypy, and ruff, all green in about two seconds. No network anywhere in the suite.
✓Each attacker move is one test driven end-to-end through the real gate over an in-memory forge: laundering, validator deletion, force-push after approve, token replay, self-hosted runners, duplicate evidence.
✓Adversarial suites for the JWT verifier and the sealing path; malformed inputs fail closed with a posted, legible failing check.
✓Whatever only runs live (signing, token minting, the REST calls) is labeled as such in the docs instead of being faked into a passing unit test.

TRY IT · NO GITHUB NEEDED

Five minutes, entirely on your machine.

$ git clone https://github.com/siglum-dev/siglum && cd siglum $ python -m pip install -e ".[dev]" # generate a fixture repo with a deliberately hollow gate $ siglum demo scaffold --out /tmp/miasma-demo --repo your-org/miasma-demo $ cd /tmp/miasma-demo # see the gap, then see what a ready install looks like $ siglum audit --config siglum-audit-config.json $ siglum setup check --local .

The scaffold contains the whole story in one directory: a spoofable required check, the Siglum policy and workflows that close it, and the preflight that verifies the install. Nothing needs a token.
